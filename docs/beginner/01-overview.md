# 第 1 章 什么是 CodeFuse-Query

## 1.1 一句话概括

**CodeFuse-Query 是一个数据中心的静态代码分析系统**：通过"语言抽取器"把源码转换成标准化的**代码数据**，再通过声明式查询语言 **Gödel** 在数据上完成各种分析任务。

## 1.2 与"传统静态分析工具"的差异

传统工具（PMD、Checkstyle、Clang Static Analyzer、Coverity、SonarQube 的插件体系）通常具备以下特征：

- 工具与特定检查目标强绑定，加一条新规则往往需要改工具代码或写插件 SDK。
- 分析逻辑通常用命令式代码实现，混入了解析、遍历、输出的细节。
- 难以横跨多种语言复用同一套分析逻辑。
- 难以在百万到亿行规模的代码库上做灵活、即席的分析。

CodeFuse-Query 的应对方式：

| 传统范式 | CodeFuse-Query 范式 |
| --- | --- |
| 工具中心：为某个目标写一个工具 | 数据中心：把代码变成数据，分析即查询 |
| 用命令式代码写分析 | 用声明式 Gödel/Datalog 写分析 |
| 每门语言一套工具链 | 统一 COREF 模型 + 每语言一个抽取器 |
| 分析结果散落在工具输出里 | 结果是结构化数据（JSON / CSV / SQLite / SARIF），可入库、可联动 |

## 1.3 三大组成部分

整体架构（见仓库 `doc/2_introduction.md`）由三部分组成：

```
┌─────────────────────────────────────────────────────────────┐
│  ① 代码数据模型 COREF                                        │
│     各语言抽取器 → AST/ASG/CFG/PDG/CallGraph/ClassHierarchy   │
│              /Documentation → 关系表（SQLite / Soufflé facts）│
├─────────────────────────────────────────────────────────────┤
│  ② 代码查询 DSL：Gödel                                        │
│     基于 Datalog 的声明式语言，描述"事实 + 规则"，自动推导      │
├─────────────────────────────────────────────────────────────┤
│  ③ 平台产品化                                                │
│     Sparrow CLI（本地）/ Query 中心（在线服务）                │
└─────────────────────────────────────────────────────────────┘
```

### ① 代码数据模型 COREF

> **COREF** = AST（抽象语法树）+ ASG（抽象语义图）+ CFG（控制流图）+ PDG（程序依赖图）+ Call Graph（函数调用图）+ Class Hierarchy（类继承）+ Documentation（注释/文档）

- 每种语言由一个**抽取器**（Extractor）把源码转换为 COREF 关系表。
- COREF 数据以**关系型数据表**存储（当前实现落地为 SQLite 数据库 + Soufflé facts）。
- 注意：**并非所有语言都实现了全部信息**。基础信息是 AST、ASG、Call Graph、Class Hierarchy、Documentation；CFG 和 PDG 仍在建设中。
- 各语言成熟度不同（见下表，来自仓库 README）：

| 语言 | 状态 | COREF 模型节点数 |
| --- | --- | --- |
| Java | 成熟 | 162 |
| XML | 成熟 | 12 |
| TS/JS | 成熟 | 392 |
| Go | 成熟 | 40 |
| OC/C++ | Beta | 53 / 397 |
| Python3 | Beta | 93 |
| Swift | Beta | 248 |
| SQL | Beta | 750 |
| Properties | Beta | 9 |

> **注意**：表中 C++ 的 "397" 指其 COREF 模型节点规模（实体表数量在 `Models.hpp` 中为 59 张表，另有继承层级与属性）。C++ 处于 **Beta** 阶段，这是后面评估的关键事实。

### ② 代码查询 DSL：Gödel

- Gödel 基于逻辑推理语言 **Datalog**，通过描述"事实（Fact）"和"规则（Rule）"不断推导出新事实。
- 继承 Datalog 的**单调性**与**终止性**：牺牲部分表达能力，换取更高的计算性能和可预期的收敛。
- 为什么不用 SQL？Gödel 相比 SQL 的天然优势是**递归**与**多表联合查询**，这两类问题（如"从入口到任意被调用方的全部调用链"）在 SQL 中非常难写。
- 为什么不用 SDK？声明式写法用户不需要关注中间计算过程，像 SQL 一样描述需求即可。

### ③ 平台产品化

- **Sparrow CLI**：包含全部组件（抽取器、数据模型、编译器、查询执行器），本地完成"抽取 → 查询"全流程。
- **Query 中心**：在线服务，供企业内大规模查询调度使用。
- 开源仓库主要交付 Sparrow CLI 及其构建体系（Bazel）。

## 1.4 已落地的企业级场景

据仓库文档（`doc/2_introduction.md`、`doc/user_case.md`），CodeFuse-Query 在蚂蚁集团支撑了：

- **CodeFuse 大模型数据清洗**：多语言漏洞扫描、代码画像（10 种语言 117 种标签、40MB/s）、AST/DFG 特征提取（准确率约 97%）。
- **代码度量评估（广目）**：复杂度、注释率、标准开发量、复用度。
- **研发风险控制 / 变更分析（优酷）**：按"文件+行号"的变更内容识别方法、入口（HTTP/HSF）、从入口到变更方法的调用链路、数据库操作影响面。
- **隐私安全分析、代码智能、终端包大小治理**等，服务月均调用量超百万。
