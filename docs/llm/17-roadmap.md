# 第 17 章 结合落地路线与验证

> 本章给出「CodeFuse-Query ↔ mcp-language-server」结合的落地步骤，重点是先验证成败开关——C++ 抽取覆盖率，再分阶段推进。

## 17.1 三个现实约束（先认账）

结合方案的价值成立，但有三道硬约束：

| 约束 | 影响 | 来源（第 11、13 章） |
| --- | --- | --- |
| C++ 抽取器 Beta | 无 CFG/PDG/注释，调用图需自建 join，oid 位置敏感 | `CorefASTVisitor.cpp` 能力边界 |
| 数据新鲜度 | 离线抽取滞后于代码变更，C++ 无增量抽取 | 仅 Java 有 `--incremental` |
| 运维成本 | 需维护抽取流水线（compile_commands.json + Clang 13 + 全量抽取） | `main.cpp` 真实编译模型 |

其中 **C++ 抽取覆盖率**是决定结合方案成败的第一开关：如果覆盖率不达标，全量调用图、风险清单都是「残缺的全局视图」，反而会误导 LLM。

## 17.2 第一步：抽取覆盖率验证（决定成败）

在投入任何结合开发前，先跑最小闭环实验：

```bash
# 1. 在电信库的某个子系统生成编译数据库
cmake -S <子系统> -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
# 或用 bear 包装现有构建

# 2. 抽取
sparrow database create -s <含compile_commands.json的目录> -lang cfamily -o ./db

# 3. 观察抽取日志：成功编译的编译单元数量 vs 总数
```

### 17.2.1 覆盖率判定

| 指标 | 判定 |
| --- | --- |
| 编译单元成功率 > 90% | ✅ 结合方案可行，继续推进 |
| 70%–90% | ⚠️ 部分模块可用，需按子系统分片 |
| < 70% | ❌ 全量图/风险清单残缺，退回替代方案（见 17.5） |

### 17.2.2 关键风险点（对应第 11 章）

- **Clang 13 兼容性**：电信代码常用 GNU 扩展、专有编译器、新 C++ 标准 → 用 `--extra-arg` 注入 `-std=gnu++17` 等方言参数尝试。
- **系统头文件排除**：`traverseDeclIfNotVisited` 会跳过系统头文件，仅在被引用时补抽——第三方 SDK 的符号可能缺失。
- **函数指针/虚调用**：全量调用图在此处不精确（clangd 同样不精确），需在文档中明确标注这一已知精度边界，避免 LLM 误信。

## 17.3 分阶段落地路线

### 阶段 1：全量调用图数据源（结合点 1）

1. 用 Gödel 脚本（第 16 章示例）产出全量调用边 + 传递闭包。
2. 导出为 SQLite/JSON。
3. mcp 侧新增数据源：LLM 查询「X 的完整调用链」时，优先命中预计算图，clangd `callers/callees` 降级为兜底。

### 阶段 2：风险清单引导（结合点 2）

1. 用 Gödel 规则预扫危险 API、全局变量、可疑模式。
2. 风险清单注入 mcp，作为 LLM 审核的「优先看」清单。
3. 评估：审核命中率是否提升、范围是否收敛。

### 阶段 3：度量热区 + 架构上下文（结合点 3、4）

1. 复杂度/扇入扇出度量 → 审核优先级排序。
2. 类继承/依赖图 → 审核类的架构上下文。

### 阶段 4：研究闭环（结合点 5）

1. Gödel 验证新规则/度量。
2. 产出回灌审核流程。

## 17.4 数据新鲜度策略

- **全量周期重抽**：C++ 无增量，建议按「日/周」级别周期全量重抽（依赖抽取时长，见第 13 章）。
- **变更触发**：用文件监视器（mcp 已有 watcher）感知变更，标记预计算数据过期，触发局部重抽或等待下一轮全量。
- **明确标注数据时间戳**：注入 LLM 的全局知识必须带「抽取时间戳」，避免 LLM 把过期数据当实时事实。

## 17.5 替代方案（若抽取覆盖率不达标）

若 C++ 抽取覆盖率 < 70%，结合点 1/2 的实际效果会打折扣，此时退而求其次：

| 目标 | 替代方案 |
| --- | --- |
| 全量调用图 | clangd 索引导出（`clangd-indexer`）或 CodeQL 的调用图导出 |
| 风险预扫描 | clangd `diagnostics` + 自定义 clang-tidy 规则 |
| 度量热区 | 轻量 AST 工具（tree-sitter 度量，mcp 已内置） |

> 这些替代方案牺牲了「声明式全量推导」的能力，但避免引入整套 CodeFuse-Query 抽取流水线的运维成本。

## 17.6 决策树

```
需要全量调用链/风险清单吗？
├── 否 → 只用 mcp-language-server（clangd + tree-sitter + rg），无需 CodeFuse-Query
└── 是 → C++ 抽取覆盖率达标吗？
    ├── 是（>90%）→ 引入 CodeFuse-Query 预计算层，按 17.3 分阶段推进
    └── 否（<70%）→ 用替代方案（17.5），CodeFuse-Query 只作静态分析研究载体（结合点 5）
```

## 17.7 小结

- 结合的价值在「全局视野」，成败开关在「C++ 抽取覆盖率」。
- **先做覆盖率验证（半天级实验），再决定投入**。
- 分阶段推进，优先结合点 1（调用链）+ 2（风险清单），它们对 LLM 审核质量提升最直接。
- 时刻标注数据新鲜度，避免过期数据误导 LLM。
